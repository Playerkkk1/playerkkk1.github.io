# Day 1:Spring Boot  入门笔记

## 1. Controller 是干什么的？

在 Spring Boot Web 项目中，Controller 主要负责：

> **接收前端发送的 HTTP 请求，并把处理结果返回给前端。**

当前项目的基本调用链：

```text
前端
 ↓ HTTP请求
Controller
 ↓
Mapper
 ↓ SQL
MySQL
```

查询完成后：

```text
MySQL
 ↓
Mapper
 ↓
Java对象
 ↓
Controller
 ↓
JSON
 ↓
前端
```

目前学习阶段采用：

```text
Controller → Mapper → MySQL
```

以后项目结构会逐渐升级为：

```text
Controller → Service → Mapper → MySQL
```

---

## 2. 当前 TaskController

```java
@RestController

// 当前 Controller 里面的接口统一以 /api/tasks 开头
@RequestMapping("/api/tasks")
public class TaskController {

    // TaskController 工作需要一个 TaskMapper
    private final TaskMapper taskMapper;

    // 构造器注入
    public TaskController(TaskMapper taskMapper) {
        this.taskMapper = taskMapper;
    }

    // 处理 GET /api/tasks
    @GetMapping
    public List<Task> findAll() {
        return taskMapper.findAll();
    }

    // 处理 POST /api/tasks
    @PostMapping
    public int createTask(@RequestBody Task task) {
        return taskMapper.insert(task);
    }
}
```

目前实现了两个接口：

```text
GET  /api/tasks    查询所有任务
POST /api/tasks    创建一个任务
```

---

## 3. `@RestController`

```java
@RestController
public class TaskController {
}
```

`@RestController` 是一个 Spring 注解。

可以暂时理解为告诉 Spring：

> 这个类是一个 Controller，负责接收 HTTP 请求，并且方法返回的数据直接作为 HTTP 响应返回。

没有这个注解时：

```java
public class TaskController {
}
```

它本质上只是一个普通 Java 类。

---

## 4. `@RequestMapping`

```java
@RequestMapping("/api/tasks")
```

作用：

> 给当前 Controller 设置统一的 URL 前缀。

所以：

```text
TaskController
      ↓
/api/tasks
```

当前 Controller 中的接口都会以：

```text
/api/tasks
```

开头。

---

## 5. HTTP 请求方式

目前最常见的四种：


| 请求方式 | 主要用途 |
| ------ | ---- |
| GET | 查询 |
| POST | 新增 |
| PUT | 修改 |
| DELETE | 删除 |


例如任务系统可以设计：

```text
GET    /api/tasks       查询所有任务

POST   /api/tasks       创建任务

PUT    /api/tasks/1     修改 id=1 的任务

DELETE /api/tasks/1     删除 id=1 的任务
```

---

## 6. `@GetMapping`

代码：

```java
@GetMapping
public List<Task> findAll() {
    return taskMapper.findAll();
}
```

类上已经存在：

```java
@RequestMapping("/api/tasks")
```

方法上存在：

```java
@GetMapping
```

组合起来就是：

```text
GET /api/tasks
```

当用户发送：

```text
GET /api/tasks
```

Spring 会找到：

```java
findAll()
```

并执行这个方法。

---

## 7. `List<Task>` 是什么？

```java
public List<Task> findAll()
```

这里仍然是普通 Java。

`List<Task>` 表示：

> 一个保存多个 Task 对象的 List 集合。

例如：

```text
List<Task>
 │
 ├── Task{id=1, title="学Java"}
 ├── Task{id=2, title="学Spring Boot"}
 └── Task{id=3, title="写项目"}
```

所以：

```java
public List<Task> findAll()
```

表示：

> `findAll()` 方法执行结束后，会返回一个装有多个 Task 对象的 List。

---

## 8. `taskMapper.findAll()`

代码：

```java
return taskMapper.findAll();
```

可以拆成：

```text
taskMapper
    ↓
调用 findAll()
    ↓
TaskMapper
    ↓
执行 SELECT SQL
    ↓
MySQL
```

例如 Mapper 中：

```java
@Select("SELECT * FROM task")
List<Task> findAll();
```

执行：

```sql
SELECT * FROM task;
```

查询数据库中的所有任务。

## 9. 数据库数据如何变成 Java 对象？

假设数据库：

```text
id    title               completed

1     学习Java             false
2     学习Spring Boot      false
```

Java 中存在：

```java
public class Task {

    private Integer id;
    private String title;
    private Boolean completed;
}
```

MyBatis 查询数据库后，会把数据库记录映射成 Java 对象。

例如：

```text
数据库一行

id = 1
title = "学习Java"
completed = false

        ↓ MyBatis 映射

Task对象

Task
 ├── id = 1
 ├── title = "学习Java"
 └── completed = false
```

多条数据库记录：

```text
数据库多行
    ↓
多个 Task 对象
    ↓
List<Task>
```

---

## 10. Java 对象如何返回给前端？

Controller 返回的是：

```java
List<Task>
```

但是前端并不直接使用 Java 对象。

Spring Boot 会自动把 Java 对象转换成 JSON。

例如：

```text
List<Task>
    ↓
Spring Boot 自动转换
    ↓
JSON
```

最终前端可能收到：

```json
[
    {
        "id": 1,
        "title": "学习Java",
        "completed": false
    },
    {
        "id": 2,
        "title": "学习Spring Boot",
        "completed": false
    }
]
```

因此 GET 请求完整流程：

```text
前端
 │
 │ GET /api/tasks
 ↓
Spring Boot
 ↓
TaskController
 ↓
findAll()
 ↓
taskMapper.findAll()
 ↓
TaskMapper
 ↓
SELECT * FROM task
 ↓
MySQL
 ↓
数据库记录
 ↓
MyBatis
 ↓
Task对象
 ↓
List<Task>
 ↓
Controller
 ↓
Spring Boot
 ↓
JSON
 ↓
前端
```

## 11. 什么是“依赖”？

`TaskController` 想要操作数据库，需要使用：

```java
TaskMapper
```

因此：

```text
TaskController
      │
      │ 依赖
      ↓
TaskMapper
```

可以说：

> TaskController 依赖 TaskMapper。

---

## 12. `private final TaskMapper taskMapper`

代码：

```java
private final TaskMapper taskMapper;
```

拆开理解：

### `private`

表示：

> 这个变量主要由 TaskController 自己使用。

### `TaskMapper`

变量的数据类型。

### `taskMapper`

变量名称。

### `final`

表示：

> 初始化之后，这个变量不能再指向另一个 TaskMapper。

整体可以理解成：

> TaskController 内部保存着一个 TaskMapper，并且初始化之后不准备再更换。

---

## 13. 构造器注入

代码：

```java
public TaskController(TaskMapper taskMapper) {
    this.taskMapper = taskMapper;
}
```

这是：

> **构造器注入**

TaskController 工作需要 TaskMapper，但是我们没有自己：

```java
new TaskMapper();
```

而是交给 Spring。

执行思路：

```text
Spring 启动
 ↓
发现 @RestController
 ↓
发现 TaskController
 ↓
准备创建 TaskController
 ↓
检查构造方法
 ↓
发现需要 TaskMapper
 ↓
Spring 找到 TaskMapper
 ↓
把 TaskMapper 传入构造器
 ↓
TaskController 创建成功
```

可以简单理解成：

```text
TaskController：

“Spring，我工作需要一个 TaskMapper。”

Spring：

“可以，我创建你的时候给你。”
```

这就是 Spring 中非常重要的：

> **DI —— Dependency Injection，依赖注入**

## 15. `@RequestBody`

假设前端发送：

```text
POST /api/tasks
```

同时发送 JSON：

```json
{
    "title": "完成Java作业",
    "completed": false
}
```

方法：

```java
public int createTask(@RequestBody Task task)
```

这里：

```java

```

可以理解成：

> Spring，把 HTTP 请求体中的 JSON 转换成一个 Task Java 对象。

转换过程：

```text
JSON

{
    "title": "完成Java作业",
    "completed": false
}

        ↓

@RequestBody

        ↓

Task对象

task
 ├── title = "完成Java作业"
 └── completed = false
```

因此进入方法以后：

```java
task
```

已经是一个有数据的 Java 对象。

## 16. `taskMapper.insert(task)`

接下来：

```java
taskMapper.insert(task);
```

就是把 Task 对象交给 Mapper。

过程：

```text
Task对象
 ↓
TaskMapper
 ↓
INSERT SQL
 ↓
MySQL
```

例如：

```text

title = "完成Java作业"
completed = false

        ↓

        ↓

MySQL

        ↓

```

## 17. 为什么 POST 返回 `int`？

代码：

```java
public int createTask(...)
```

因为：

```java
taskMapper.insert(task)
```

通常返回 SQL 操作：

> **影响了多少行数据。**

如果成功新增一条：

```text
返回 1
```

这里的 `1` 通常表示：

```text
成功影响 1 行数据
```

而不是：

```text
新增任务的 id = 1
```

这一点需要特别区分。

```text
 ↓
```

## 2. 最重要的三层结构

目前项目主要是：

```
TaskController
      ↓
TaskService
      ↓
TaskMapper
      ↓
    MySQL
```

## Controller：负责 HTTP

例如：

```
@GetMapping("/{id}")
public Task findById(@PathVariable Integer id) {
    return taskService.findById(id);
}
```

它关心的是：

```
用户发了什么请求？
请求地址是什么？
参数在哪里？
返回什么？
```

所以会出现：

```
@GetMapping
@PostMapping
@PutMapping
@DeleteMapping

@PathVariable
@RequestBody
```

---

## Service：负责业务逻辑

例如：

```
public Task findById(Integer id) {
    return taskMapper.findById(id);
}
```

目前我们的业务还非常简单，所以 Service 看起来像一个“中转站”。

但以后它会负责：

```
判断任务是否存在
↓
检查任务状态
↓
处理截止时间
↓
处理 AI 提取结果
↓
调用 Mapper
```

所以：

> Controller 不应该直接操作数据库，业务逻辑主要放 Service。

## Mapper：负责数据库操作

这是今天你比较容易迷糊的地方。

记住一句：

> **TaskMapper 是 Java 和 MySQL 之间的数据库操作接口。**

例如：

```
@Select("SELECT * FROM task WHERE id = #{id}")
Task findById(Integer id);
```

调用：

```
taskMapper.findById(3);
```

大致发生：

```
Java
taskMapper.findById(3)
        ↓
MyBatis
        ↓
SELECT * FROM task WHERE id = 3
        ↓
MySQL
        ↓
查询结果
        ↓
MyBatis 转成 Task
        ↓
Java得到 Task 对象
```

## 3. Mapper 为什么只有 interface 也能运行？

例如：

```
@Mapper
public interface TaskMapper {
}
```

我们根本没有自己写：

```
new TaskMapper();
```

也没有：

```
class TaskMapperImpl implements TaskMapper
```

原因是：

```
你定义 TaskMapper 接口
        ↓
MyBatis 读取它
        ↓
MyBatis 动态生成代理实现
        ↓
Spring 管理这个对象
        ↓
注入 TaskService
```

所以：

```
private final TaskMapper taskMapper;
```

这里真正工作的，是 **MyBatis 创建的代理对象**。

这是今天非常值得记住的知识点。

---

## 4. `#{}` 到底是什么

例如：

```
int update(Task task);
```

Task 里面：

```
id = 4
title = "数据库作业"
status = "DONE"
```

Mapper：

```
UPDATE task
SET title = #{title},
    status = #{status}
WHERE id = #{id}
```

MyBatis 会从 Task 中取：

```
#{title}
↓
task.getTitle()

#{status}
↓
task.getStatus()

#{id}
↓
task.getId()
```

所以：

```
#{status}
```

不是普通字符串。

它代表：

> 从传入参数/对象中取得对应数据，然后绑定到 SQL。

---

## 5. PUT 是今天最值得理解的一条链

请求：

```
PUT /api/tasks/4
```

JSON：

```
{
  "title": "数据库作业",
  "status": "TODO"
}
```

这里有两个数据来源。

URL：

```
/api/tasks/4
           ↑
          id
```

通过：

```
@PathVariable Integer id
```

得到：

```
id = 4
```

JSON 则通过：

```
@RequestBody Task task
```

转换成：

```
Task
├── id = null
├── title = "数据库作业"
└── status = "TODO"
```

Spring **不会自动把 URL 中的 `4` 塞进 Task.id**。

所以我们需要：

```
task.setId(id);
```

最终：

```
Task
├── id = 4
├── title = "数据库作业"
└── status = "TODO"
```

再：

```
return taskService.updateTask(task);
```

最终 Mapper 才能：

```
WHERE id = #{id}
```

拿到 `4`。

所以一句话：

> **URL 中的 id 决定“修改谁”，JSON 中的 Task 决定“修改成什么”。**

---

## 6. `@PathVariable` 和 `@RequestBody`

这个必须区分。

### `@PathVariable`

从 URL 中拿：

```
GET /api/tasks/4
@PathVariable Integer id
```

得到：

```
id = 4
```

---

### `@RequestBody`

从 HTTP 请求体中的 JSON 拿：

```
{
  "title": "Java作业"
}
```

经过：

```
@RequestBody Task task
```

变成：

```
task.getTitle()
→ "Java作业"
```

因此：

```
@PathVariable
URL → Java变量

@RequestBody
JSON → Java对象
```

## 7. HTTP 和 SQL 不要混

今天 Apifox 测试时还碰到了一个很有价值的错误。

修改接口使用：

```
PUT
```

数据库修改语句才叫：

```
UPDATE
```

完整关系：

```
Apifox
PUT /api/tasks/4
      ↓
Controller
@PutMapping
      ↓
Service
      ↓
Mapper
@Update
      ↓
MySQL
UPDATE task ...
```

所以：

> HTTP 层：PUT
> SQL 层：UPDATE

## 8. 今天遇到的 405

返回：

```
405 Method Not Allowed
```

它通常意味着：

> 地址可能存在，但是当前 HTTP Method 不允许。

例如接口只支持：

```
@PutMapping("/{id}")
```

却发送了错误的 HTTP Method，就可能出现 405。

以后看到状态码，可以先形成基本反应：

```
404 → 路径/资源可能不存在

405 → HTTP Method 不匹配

500 → 请求进入后端后，执行过程中出错
```

这只是初步判断，不是看到状态码就直接下结论。

```
[
  {
    "id": 1,
    "title": "Java作业"
  }

```

这个：

```
Java对象 → JSON
```

叫：

> **序列化**

所以：


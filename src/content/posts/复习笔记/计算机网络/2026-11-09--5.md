# 05｜运输层

## 一、运输层的基本概念

运输层是计算机网络体系结构中的第四层，位于应用层和网络层之间。

主要任务是为运行在不同主机上的应用进程提供端到端的通信服务。

例如：

当浏览器访问 Java 后端服务器时，浏览器中的应用进程需要与服务器上的应用进程进行通信，这个过程需要运输层提供支持。

运输层主要功能：

1. 提供进程之间的通信。
2. 实现复用和分用。
3. 提供可靠或尽力而为的数据传输服务。
4. 实现流量控制。
5. 实现拥塞控制。

## 二、运输层的两个重要协议

运输层最重要的两个协议是：

- TCP：传输控制协议。
- UDP：用户数据报协议。

### 1. TCP 协议

TCP 全称：

Transmission Control Protocol

主要特点：

- 面向连接。
- 提供可靠传输。
- 面向字节流。
- 提供流量控制。
- 提供拥塞控制。
- 需要进行连接管理。

TCP 在正式传输数据之前，需要先建立连接。

### 2. UDP 协议

UDP 全称：

User Datagram Protocol

主要特点：

- 无连接。
- 不保证可靠交付。
- 面向报文。
- 没有连接建立和释放过程。
- 不提供 TCP 那样的流量控制和拥塞控制机制。

UDP 协议本身不保证数据一定到达接收端。

### 3. TCP 与 UDP 对比


| 比较项目 | TCP | UDP |
| ---- | --------- | ---------- |
| 连接方式 | 面向连接 | 无连接 |
| 可靠性 | 可靠传输 | 不保证可靠交付 |
| 数据形式 | 字节流 | 数据报文 |
| 流量控制 | 有 | 无 |
| 拥塞控制 | 有 | 无 |
| 传输效率 | 管理机制较复杂 | 首部开销较小 |
| 常见应用 | HTTP、文件传输 | DNS、实时音视频等 |


注意：

UDP 并不意味着数据一定会丢失，TCP 也不意味着数据一定不会丢失。区别在于协议本身是否提供可靠传输机制。

## 三、端口与套接字

### 1. 端口

IP 地址用于标识主机或网络接口，端口号用于标识主机上的应用进程。

端口号长度为 16 bit。

取值范围：

0～65535。

常见端口号：


| 协议 | 常见端口 |
| -------- | ---- |
| FTP 控制连接 | 21 |
| SSH | 22 |
| Telnet | 23 |
| SMTP | 25 |
| DNS | 53 |
| DHCP 服务器 | 67 |
| DHCP 客户端 | 68 |
| HTTP | 80 |
| POP3 | 110 |
| HTTPS | 443 |


### 2. 端口号分类

- 熟知端口：0～1023。
- 注册端口：1024～49151。
- 动态或私有端口：49152～65535。

### 3. 套接字 Socket

套接字是网络通信中使用的重要概念。

在 TCP 通信中，一个连接通常由以下四个值共同确定：

- 源 IP 地址
- 源端口号
- 目的 IP 地址
- 目的端口号

也就是常说的四元组。

## 四、UDP 协议

UDP 是一种简单的运输层协议。

### 1. UDP 首部

UDP 首部固定为 8 Byte。

包含四个字段：


| 字段 | 长度 | 作用 |
| ---- | ------ | ------------ |
| 源端口 | 16 bit | 发送端端口 |
| 目的端口 | 16 bit | 接收端端口 |
| 长度 | 16 bit | UDP 首部与数据总长度 |
| 检验和 | 16 bit | 差错检测 |


### 2. UDP 的主要特点

- 无连接。
- 面向报文。
- 没有复杂的连接管理。
- 首部开销小。
- 支持一对一、一对多、多对一等通信方式。

### 3. UDP 适用场景

- DNS 查询。
- 实时音视频。
- 在线游戏。
- 一些对实时性要求较高的通信场景。

## 五、TCP 协议

TCP 是一种面向连接、提供可靠传输服务的运输层协议。

### 1. TCP 的主要特点

1. 面向连接。
2. 点对点通信。
3. 可靠交付。
4. 全双工通信。
5. 面向字节流。
6. 支持流量控制。
7. 支持拥塞控制。

### 2. TCP 报文段首部

TCP 首部的基本固定长度为 20 Byte。

常见字段：


| 字段 | 作用 |
| ---- | ----------------- |
| 源端口 | 发送端应用进程端口 |
| 目的端口 | 接收端应用进程端口 |
| 序号 | 标识数据字节的位置 |
| 确认号 | 表示期望收到的下一个字节序号 |
| 数据偏移 | 标识 TCP 首部长度 |
| 控制位 | SYN、ACK、FIN、RST 等 |
| 窗口 | 通告接收窗口大小 |
| 检验和 | 检测差错 |
| 紧急指针 | 与紧急数据有关 |


### 3. TCP 的序号与确认号

TCP 采用字节编号。

假设发送端发送 1000 Byte 数据，初始序号为 100。

那么：

- 第一个字节序号为 100。
- 最后一个字节序号为 1099。
- 接收端确认号为 1100。

确认号表示接收端期望收到的下一个字节序号。

## 六、TCP 可靠传输

TCP 通过一系列机制实现可靠传输。

主要包括：

- 序号与确认号。
- 检验和。
- 超时重传。
- 冗余确认。
- 滑动窗口。
- 按序交付。

### 1. 序号与确认号

每个 TCP 字节都有对应的序号。

接收端通过确认号告诉发送端，自己下一步期望接收哪个字节。

### 2. 超时重传

发送端发送数据后，如果在规定时间内没有收到确认，就会重新发送相关数据。

### 3. 累积确认

TCP 通常采用累积确认机制。

例如：

接收端已经正确收到 1～1000 号字节。

那么确认号可以为 1001。

表示 1001 之前的数据已经连续收到。

## 七、停止等待协议与滑动窗口

### 1. 停止等待协议

发送端发送一个数据分组后，需要等待接收端确认，收到确认后才能继续发送下一个分组。

优点：

- 实现简单。
- 容易保证数据顺序。

缺点：

- 信道利用率较低。
- 发送端需要频繁等待确认。

### 2. 滑动窗口

滑动窗口允许发送端在收到确认之前，连续发送多个数据。

主要目的：

提高通信效率。

### 3. 滑动窗口的基本原理

发送窗口：

表示发送端当前允许连续发送的数据范围。

接收窗口：

表示接收端当前能够接收的数据范围。

当发送端收到新的确认后，发送窗口可以向前移动。

这个过程称为窗口滑动。

### 4. 窗口示意

假设发送窗口大小为 4：


| 序号 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 状态 | 可发送 | 可发送 | 可发送 | 可发送 | 未开放 | 未开放 | 未开放 | 未开放 |


发送端发送前四个数据后，收到确认，窗口可以向后移动。

## 八、流量控制

流量控制的目的是防止发送端发送数据过快，导致接收端来不及处理。

TCP 主要通过接收窗口实现流量控制。

### 基本过程

1. 接收端根据自身缓存情况通告接收窗口大小。
2. 发送端根据接收窗口限制发送的数据量。
3. 接收端处理数据后更新窗口。
4. 发送端根据新的窗口信息调整发送速度。

### 流量控制的核心

让发送端的发送速度与接收端的接收能力相适应。

## 九、拥塞控制

拥塞控制的目的是防止过多的数据进入网络，导致网络负载过高。

### 1. 拥塞的表现

- 数据包排队时间增加。
- 数据包丢失。
- 网络时延增加。
- 网络传输效率下降。

### 2. 拥塞控制与流量控制的区别


| 比较项目 | 流量控制 | 拥塞控制 |
| ---- | ---------- | --------- |
| 主要目的 | 防止接收端处理不过来 | 防止网络负载过高 |
| 关注对象 | 接收端 | 整个网络 |
| 主要机制 | 接收窗口 rwnd | 拥塞窗口 cwnd |


### 3. 拥塞控制的主要算法

#### 慢开始

连接刚开始传输时，拥塞窗口从较小值开始增长。

随着传输成功，拥塞窗口逐步扩大。

#### 拥塞避免

当拥塞窗口达到一定阈值后，增长速度通常会降低，进入较平缓的增长阶段。

#### 快重传

发送端连续收到多个重复确认时，可以推断某个报文段可能丢失，并提前重传。

#### 快恢复

在特定拥塞处理机制下，发送端不必完全回到最初状态，而是调整拥塞窗口后继续传输。

注意：这些是经典 TCP 拥塞控制算法的基本思想，实际 TCP 实现还存在不同算法和版本。

## 十、TCP 三次握手

TCP 在正式传输数据之前，需要通过三次握手建立连接。

### 三次握手过程

**第一次：客户端发送 SYN**

客户端向服务器发送连接请求，并设置 SYN = 1。

**第二次：服务器返回 SYN + ACK**

服务器收到请求后，返回 SYN = 1、ACK = 1 的报文。

**第三次：客户端返回 ACK**

客户端收到服务器响应后，再发送 ACK = 1 的报文。

至此，TCP 连接建立成功。

### 为什么需要三次握手？

主要目的是：

1. 确认客户端的发送能力。
2. 确认服务器的发送和接收能力。
3. 确认客户端能够接收服务器的数据。
4. 同步双方的初始序号。

## 十一、TCP 四次挥手

TCP 连接释放通常需要四次挥手。

### 四次挥手过程

**第一次：客户端发送 FIN**

客户端表示自己已经没有数据需要发送，希望关闭连接。

**第二次：服务器返回 ACK**

服务器确认收到客户端的关闭请求。

此时客户端到服务器方向的数据发送已经结束，但服务器仍可能继续发送数据。

**第三次：服务器发送 FIN**

服务器处理完剩余数据后，发送 FIN 请求关闭连接。

**第四次：客户端返回 ACK**

客户端确认服务器的关闭请求。

随后客户端等待一段时间后，进入 CLOSED 状态。

### 为什么通常是四次挥手？

因为 TCP 是全双工通信。

两个方向的数据传输需要分别关闭。

服务器收到 FIN 后，可以先确认客户端的关闭请求，但不一定能够立即关闭自己到客户端的发送方向。

因此通常需要两次 FIN 和两次 ACK。

## 十二、三次握手与四次挥手对比


| 比较项目 | 三次握手 | 四次挥手 |
| ---- | --------------- | --------------- |
| 主要目的 | 建立连接 | 释放连接 |
| 过程 | SYN、SYN+ACK、ACK | FIN、ACK、FIN、ACK |
| 主要原因 | 同步双方初始序号 | 两个方向分别关闭 |
| 结果 | 建立 TCP 连接 | 释放 TCP 连接 |


## 十三、常见易混淆知识点

### 1. TCP 与 UDP

TCP 面向连接，提供可靠传输。

UDP 无连接，不保证可靠交付。

### 2. 流量控制与拥塞控制

流量控制关注接收端能力。

拥塞控制关注网络整体负载。

### 3. 序号与确认号

序号表示当前数据字节的位置。

确认号表示期望收到的下一个字节序号。

### 4. 三次握手与四次挥手

三次握手用于建立连接。

四次挥手用于释放连接。

### 5. 运输层与网络层

网络层实现主机到主机的通信。

运输层实现进程到进程的通信。
